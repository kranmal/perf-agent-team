Performance test strategy

lendly · Static web build served from GitHub Pages (https://kranmal.github.io/lendly/) and a local copy of dist/ · 2026-10-22 · analysed from codebase
Status: proposal for approval. No performance tests have been written or run. Answer the open questions and approve (or amend) the test plan before the build phase starts.

1. Summary

Lendly has no backend. It is an Expo/React Native app exported as a static web site; all data lives in the browser (AsyncStorage, which is localStorage on web). A classic server load test (hundreds of virtual users) would only hammer GitHub Pages, which is not ours to load and which scales on its own. The real performance risks are on the client: a 1.1 MB (314 KB gzipped) single JavaScript bundle on first load, and data-handling code that gets slower as a user's lists grow (every list item recomputes all active loans, nothing is virtualised, and every change rewrites all stored data). The proposed strategy therefore measures (1) first-load speed and delivery, (2) client performance at 100 / 1,000 / 5,000 / 20,000 records, and (3) a small, polite k6 check of static delivery against a local copy only. Traffic-style load, stress and spike tests against the live site are explicitly out of scope.

5. Workload model

Concurrent users: not applicable: the server work per user is a static file fetch · Peak requests/s: unknown · Basis: No analytics available to the analysis. Dataset sizes below are assumptions about plausible personal use.

  • Typical user: 10 to 100 items, 5 to 30 people, 20 to 300 loans (assumed).
  • Heavy user: 1,000 items, 100 people, 5,000 loans (assumed upper realistic bound).
  • Extreme test point: 20,000 loans to find where the app breaks or localStorage fills (stress equivalent).
  • Test device: desktop Chromium with 4x CPU throttling to approximate a mid-range phone (assumed), plus unthrottled.

8. Environment, data and safeguards

AspectDetail
TargetLocal only: `npx expo export -p web` then a local static server on localhost, driven by Playwright (already in e2e-tests/) and k6. Live site: at most single read-only requests (as done during this analysis).
Test dataSynthetic generated items, people and loans injected into localStorage. No real data exists server-side.
Safeguards
  • No load test against kranmal.github.io, GitHub Pages or AdSense (not ours, terms of service, no benefit).
  • k6 host guard allows localhost only.
  • AdSense is blocked in measurement runs unless the run is explicitly the 'with ads' variant.
  • No changes to the lendly source; findings only. The perf/ folder is added uncommitted.
Monitoring
  • Chromium Performance API marks, long-task entries and JS heap size
  • Lighthouse metrics
  • k6 metrics for the local delivery check

9. Tooling

Playwright (already used in e2e-tests/) plus Lighthouse for the browser measurements, and k6 only for the local static-delivery check: The risks are in the browser, which k6 does not run. Playwright can seed localStorage, drive the UI and read performance entries. k6 adds little here but keeps the same harness and report as other projects.
Alternatives considered: JMeter or Locust would only test the server and add nothing for a client-only app. k6 browser module is possible but less mature than Playwright for this.

11. Open questions for you

  • Do you have real usage numbers (visitors per day, device mix, typical number of items and loans)? Without them the dataset sizes are assumptions.
  • Which matters more: web (SEO, first load) or the mobile apps? This plan covers web only.
  • Are you happy to measure with the AdSense ad blocked by default, plus one 'with ads' run?
  • Are the proposed SLOs (LCP < 2.5 s, add-loan < 100 ms, Items tab < 1 s at 1,000 records) the right bar?
  • Is it OK for me to add the perf/ folder to the lendly repo (uncommitted, you decide whether to commit via a PR)?

12. Not in scope

  • Load, stress or spike testing GitHub Pages or any live third-party service
  • Native iOS and Android runtime performance
  • Fixing the performance issues (findings are reported, not changed)
  • Server capacity planning: there is no server

13. What happens after approval

  1. Scripts and perf.config.json are built to this plan.
  2. Smoke test, then load, stress and spike run one at a time.
  3. A results report PDF is produced: SLO pass/fail, latency percentiles, throughput, error rates, breaking point, bottleneck notes and recommendations.
